# Key scopes can only narrow the authenticated person's authority for removes operations

The current authenticated person is resolved from the Account; an AI agent uses the person who connects it. The independently configured operation and credential Rules remain AND guards. This configured decision describes actual dispatched evaluation, not an executable grant predicate.

Session authentication has no Client/Key scope restriction. For key authentication, the actual retained key binds its Account and owning Client. Begin with ['*'] when the Account Root flag or super_admin assignment establishes Root; otherwise use its actual Role-derived codes. Apply Client scopes first, then Key scopes. An empty array or exactly ['*'] inherits the incoming codes unchanged. Every other array restricts: incoming exactly ['*'] is replaced with the unique scope codes, otherwise take their unique intersection. A mixed array containing '*' is not the unrestricted ['*'] case.

Effective Root remains only when the original base codes were ['*'] and neither scope array restricted them. If that original wildcard was restricted and the final codes still equal ['*'], replace the final codes with an empty list. An empty restricted result denies and never falls back to Account Role codes. This Rule delegates the Key step after Client narrowing. Disabled Clients, revoked/expired Keys and invalid bindings cannot authenticate. Presented credentials, intermediate sets and effective Root are runtime inputs/results, not retained facts.

## Rationale

Client and Key restrictions independently compose by AND with the requested operation's authority.
